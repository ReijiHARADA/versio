# Refactoring cadence

Versio のリファクタリングは、品質改善や機能追加と混ぜず、安定した節目で小さく行う。

## 実施するタイミング

- 抽出・翻訳・Paper Package の大きな変更が完了し、回帰テストが通った後
- 同じ責務の修正が 2〜4 回続いたとき
- 1 ファイルに複数の責務や重複した判定が集まり、次の変更範囲を予測しにくくなったとき
- `.app` の実機確認で、機能ではなく保守性・初期化順序・境界の問題が見つかったとき

本番品質の原因調査中は、まず失敗ケースを固定してからリファクタリングする。大規模な整理を並行して始めない。

## 1 回の範囲

1 回につき、密に関係する 1 責務または 1 ホットスポットだけを扱う。

- public API、保存形式、Paper Package の構造は維持する
- 先に characterization test を追加し、移動後も同じ挙動を確認する
- 新しい抽象化層・Rule Engine・クラス階層は、重複削減だけでは導入しない
- 生成物や大規模な実データ再計測は、変更の影響がある場合だけ行う

## 完了条件

変更ごとに、対象に応じて次を実行する。

1. 対象の unit / integration test
2. `npm run typecheck`
3. `npm run lint`（既存 warning と新規 warning を区別）
4. 抽出・翻訳・Package に触れた場合は該当する regression test
5. Reader / 永続化 / macOS 固有処理に触れた場合は、必要に応じて最新 `.app` で確認

完了時は `CURRENT_STATE.md` に、対象、挙動維持の根拠、実行した検証、残る課題を 1 エントリで記録する。履歴の詳細は `docs/history/` に置く。

## 優先順位

現在の抽出品質回帰を最優先にし、次の安定した節目で保守性リファクタリングを行う。翻訳品質の fallback 率を下げるためだけに、リファクタリングを品質改善と称して実施しない。
