# 抽出品質の根本改善 — 設計

日付: 2026-11-15 / 対象: Versio 学術 PDF 抽出（翻訳モデル選定は別プロジェクト）

## 1. なぜやるか

Codex `/goal` による自動改善ループを計 50 時間以上回したが、抽出・翻訳とも実用レベルに届かなかった。
原因の中心は **ループが追った指標と実感のずれ**。文書上は source integrity 0.9999 / heading recall 0.993 だが、
実際に読むと以下の「細部」が崩れている:

- タイトルの抜き出し
- 図表キャプションの取り付け（どの図・表のキャプションか）
- 著者 ↔ 所属機関の対応、連絡先（メール）
- 参考文献

人が PDF を読んでずれを判定するレビューツール（`dev:extraction-eval`）も作ったが、毎 PDF を人手で判定する運用は続かなかった。
現行実装はヒューリスティック約 2.6 万行（`pdfLayout.ts` 6k、`documentResolver.ts` 5k、`toPaper.ts` 4.9k など）で、積み増しは天井に当たっている。

## 2. ゴール / 非ゴール / アンチゴール

**ゴール**

1. 人手判定なしで、上記の細部項目を **実感に近い形で** 自動採点できる評価基盤（数百本規模）。
2. その採点で、細部項目ごとに「現行ルール / GROBID / macOS 標準機能」を実測比較し、勝った方式を項目単位で本番採用する。
3. 採用後、細部項目の採点が現行より明確に上がる（目標値は §6 で実測後に設定）。

**非ゴール**

- 翻訳モデルの選定・比較（別プロジェクト。抽出の後）。
- 本文テキスト取得・読み順の全面書き換え。本文と読み順はネイティブ pdf.js 抽出を維持する。
- 数式・表セル構造の改善（ROADMAP B2）。
- 英語・日本語以外の言語の品質保証。

**アンチゴール（技術的に動いても失敗とみなす）**

- **有料 API・課金が必要な要素を一つでも使う**（クラウド LLM による採点・抽出を含む）。
- 論文 PDF を外部サービスへ送る（実行時の処理はすべてローカル）。
- 採点値は上がったが、実際に読むと細部が良くなっていない（＝指標ずれの再発）。
- 本文テキストを GROBID / LLM の出力で置き換える（native text が正）。

## 3. 制約

- 一人開発・費用ゼロ。ツール・モデルは無料かつローカル実行、ライセンスは同梱配布可能なもの（Apache-2.0 / MIT 等。非商用・AGPL は不可）。
- 既存制約（AGENTS.md）を維持: CanonicalDocument が正、pdfjs-dist 3.11 固定、block ID 再利用、GROBID/Docling は任意 enricher で必須依存にしない、`formats/` 外に出版社別判定を増やさない、Format Profile 閾値 APPLY_MIN=0.75 / APPLY_MARGIN=0.12 を変えない。
- 正解データの PDF・XML はリポジトリにコミットしない（gitignored。取得スクリプトと manifest のみコミット）。
- 実機検証は Tauri macOS `.app` 基準。

## 4. Approaches

| 案 | 内容 | トレードオフ | 扱い |
|---|---|---|---|
| A. ルール維持 + 採点修正 | 現行ヒューリスティックのまま、ループが追う指標を JATS 採点へ差し替える | 最安。だが 2.6 万行の上に積み続ける構造は不変で、天井は残る | **比較の基準線**として計測のみ |
| B. GROBID | 学術 PDF 専用解析器（Apache-2.0、ローカル JVM）。ヘッダ（タイトル・著者・所属・メール）と参考文献を学習済みモデルで構造化 | 細部項目が得意分野。代償は JRE 同梱で数百 MB 増・起動数秒・常駐 RAM（header のみなら ~2GB 級） | **本命候補** |
| C. macOS 標準 | Vision `RecognizeDocumentsRequest`（段落/表/リスト領域）＋ Foundation Models（OS 内蔵小型 LLM）で項目を振り分け | 無料・容量増なし。macOS 26 以降必須、論文細部での精度は未知、LLM 文脈長が小さい | **比較候補** |

**採用した進め方（ユーザー承認済み）**: 採点基盤を先に作る → 同じ約 100 本で A/B/C を実測 → 項目ごとに勝った方式を採用。

## 5. 決まっていること

### 5.1 正解データ（ゴールド）

- 取得元: **Europe PMC の OA 論文の JATS XML**（無料、`/{PMCID}/fullTextXML`）。既存 `scripts/fetch-oa-europepmc.mjs` と同じ条件（`isOpenAccess=Y` + CC ライセンス）で PDF と XML を対で取得する。
- JATS から抽出する項目: `article-title`、`contrib`（著者名）、`aff`（所属）と `xref ref-type="aff"`（著者↔所属対応）、`email` / `corresp`、`fig` / `table-wrap` の `label` + `caption`、`ref-list` の各 `ref`（著者・題名・年・誌名・DOI）。
- 既存の手作り正解 15 本（`test-fixtures/real-papers/ground-truth/`）は残し、同じ採点器で併用する。

**分野の広さ（ユーザー回答）**: ユーザーが普段読むのは HCI・デザイン系だが、アプリとしては幅広い研究分野で使われることを目指す。したがってゴールドは複数の取得元を組み合わせる。

| 取得元（すべて無料） | 分野 | 取れる正解 | 弱い項目 |
|---|---|---|---|
| Europe PMC JATS | 医学・生命科学・一部社会科学 | 全項目 | — |
| arXiv LaTeX ソース | CS・HCI・物理・数理など | タイトル、著者、図表キャプション（`\caption`）、参考文献（`.bbl`） | 所属・メールは書式がばらばらで精度低 |
| J-STAGE（WebAPI と、提供誌の全文 XML） | 日本語論文（工学・デザイン・人文社会など） | タイトル（日英）、著者、所属。全文 XML 提供誌ではキャプション・参考文献 | 提供誌が限られる |

- 比較用の約 100 本は、取得元・分野・言語で層化して選ぶ（HCI・デザインを必ず含める）。項目別スコアは取得元別にも出し、全体値だけで勝者を決めない。
- 取得元ごとに「その取得元で正解が信頼できる項目」だけを採点する（例: arXiv の所属は採点しない）。

### 5.1.1 日本語論文（ユーザー回答）

- Versio は文献管理ツールでもあるため、日本語論文も管理でき、かつ抽出がうまくいくことを要件とする。
- J-STAGE 由来の日本語ゴールドを比較セットに含める（目安 15〜20 本）。
- **採用条件**: ある方式が英語で勝っても、日本語で現行より悪化する項目には採用しない。言語ごとに方式を切り替える構成（例: 英語は GROBID、日本語は現行または C）を許容する。

### 5.2 採点（項目別）

- タイトル: 正規化後の完全一致率 + 文字類似度。
- 著者: 名前リストの P/R/F1（名前正規化あり）。
- 著者↔所属: 対応ペアの F1。
- 連絡先: メールの P/R。
- キャプション: キャプション文の検出 F1 と、図/表番号との紐付け正解率。
- 参考文献: 件数一致、各文献の分割正解率（境界）、題名・年・DOI のフィールド一致率。
- 出力は「論文 × 項目」の表と、項目別の全体値。ワースト事例の一覧を必ず出す（数値だけで判断しない）。

### 5.3 指標ずれの再発防止

- 採点器の妥当性を、着手時に一度だけ人が確認する: 約 10 本について採点結果とワースト事例を人が見て「実感と合っているか」を判定する（毎 PDF ではない）。
- 以後、採用判断のたびにワースト 5 件を人が目視する手順を残す。

### 5.4 比較実験

- 同一の約 100 本（ゴールド付き）で A/B/C を実行し、§5.2 の項目別に比較する。
- B: GROBID を開発機でローカル起動（Docker 不在・Java 不在のため、JRE 導入から）。既存 `src/services/pdfExtraction/grobid/client.ts`（`processHeaderDocument`、`GROBID_URL`、クラウド URL 拒否）と `tei.ts` を土台に、参考文献（`processReferences` / fulltext）とキャプションを追加取得。
- C: Swift 側（Tauri Rust → Swift ブリッジ、既存 `ocr.rs` の Vision 呼び出し方式に倣う）で RecognizeDocuments と Foundation Models を呼ぶ試作。
- 速度（1 本あたり秒）、RAM、配布サイズ増も記録する。

### 5.5 本番採用

- 項目ごとに勝者を選ぶ。採用した外部方式の出力は **Evidence として CanonicalDocument に入れ、Resolver が採否を決める**（既存アーキテクチャ通り。本文テキストは置き換えない）。
- 採用した方式が使えない環境（GROBID 未起動、macOS 26 未満）では現行ルールへフォールバックする。
- 現行ルールはフォールバックとして残るため、ルール削除は成果に含めない。削除は「採用方式が全対象環境で常に使える」と確認できた項目に限る。

### 5.6 範囲と段階（Claude の判断）

本設計の範囲は 3 段階。段階 3 は段階 2 の結果をユーザーが確認してから、別の実装計画として立てる。

1. 採点基盤（ゴールド取得・JATS パーサ・項目別採点・A の基準線）
2. B/C の比較実験と、項目別の勝者提案（レポート）
3. 勝者の本番統合（Evidence 化・フォールバック・`.app` 確認。GROBID の同梱方式はここで設計）

### 5.7 実行環境（Claude の判断）

- A/B の比較は Node スクリプト（既存 `vite-node` の評価スクリプト群と同じ形）で回す。B は開発機でローカル起動した GROBID に `GROBID_URL` で接続する。
- C の比較は単体の Swift コマンドラインツールで回す（Tauri 経由にしない）。`.app` での確認は段階 3 の勝者だけ。
- 段階 1 の冒頭で、開発機で Foundation Models が使えるか（Apple Intelligence 有効・モデル取得済み）を確認する。使えなければ C は Vision のみで比較し、その旨を記録する。

### 5.8 ゴールドの品質（Claude の判断）

- JATS と PDF が同じ版とは限らない（PDF は Unpaywall / 出版社経由で取得されうる）。正規化後のタイトル一致と第一著者一致の両方を満たす対だけをゴールドに採用し、除外数を記録する。
- 既存の手作り正解 15 本はタイトル等の記載済み項目のみ採点する（追加の手入力はしない）。§5.3 の人手確認 10 本は JATS ゴールド側から選ぶ。

## 6. ビルダーに任せること

- JATS パーサの実装詳細、名前・文字列の正規化規則。
- 比較用サンプル約 100 本の選び方（分野・レイアウトの偏りを避ける層化）。
- 採用基準の具体的な数値（「明確に上回る」の閾値）は、A の基準線を測った後に提案し、ユーザーが確認する。
- GROBID の同梱方式（JRE 同梱 / サイドカー起動方法）の詳細は、B が採用された場合に別途設計する。
